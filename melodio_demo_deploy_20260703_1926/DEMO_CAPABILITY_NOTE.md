# Melodio Demo 能力说明与已知问题

## 1. Demo 目标

这个 demo 用来验证自然语言音乐助手的核心链路：

- 理解用户的自然语言音乐需求
- 判断一级/二级意图
- 抽取歌曲、歌手、专辑等音乐实体
- 生成推荐策略和分组
- 返回可解释的歌曲列表
- 尝试通过 Spotify / 网易云提供内嵌播放入口
- 支持轻量多轮上下文，例如引用上一轮结果中的「第二首」「这首」「刚才那首」

它目前更接近「音乐意图理解 + 推荐策略 demo」，不是完整的生产级播放器或推荐系统。

## 2. 当前支持的意图能力

### 音乐实体搜索

支持对明确音乐实体的搜索和起播识别。

典型 query：

- `周杰伦的歌`
- `播放周杰伦的晴天`
- `许嵩的《乌鸦》`
- `kanye`
- `I Knew It, I Knew You`
- `范特西`

当前策略：

- 明确歌手 + 歌名时，按单曲精搜处理。
- 明确播放某首歌时，结果只返回目标单曲。
- 明确歌手作品搜索时，返回该歌手本人多首作品，不做歌手去重。
- 专辑类 query 会尽量返回专辑实体、歌手和曲目。

### 内容推荐

支持泛推荐、场景推荐、情绪推荐、风格推荐、语言/年代/主题限定推荐。

典型 query：

- `随便来点歌`
- `适合开车听的歌`
- `适合深夜一个人听的歌`
- `丧一点但有爆发力的歌`
- `来点朋克`
- `要粤语的`
- `有没有90年代的`
- `爱情歌曲`
- `像 Billie Eilish 那种暗黑流行风`

当前策略：

- 没有明确约束时，判为泛推荐。
- 出现语言、年代、场景、情绪、主题、风格等约束时，判为曲库限定推荐。
- 对「流行歌曲」「睡前歌曲」「轻音乐」「男女对唱」这类表达，按推荐约束处理，不当作实体搜索。

### 相似推荐

支持相似歌曲、相似歌手/音色、相似风格的推荐。

典型 query：

- `和泸沽湖相似的歌`
- `和《乐队的夏天》里泸沽湖相似的歌曲`
- `类似周深音色的艺人`
- `像草东那种丧但有爆发力的歌`

当前策略：

- 先建立参照对象画像，再做分层推荐。
- 对相似歌曲，优先考虑原歌手/原乐队其他作品。
- 对有地域或圈层特征的对象，会考虑同地域、同节目、同厂牌、同独立音乐圈。
- 不只按「民谣」「摇滚」「伤感」这类泛标签推荐。

### 音乐百科 / 问答

支持音乐相关事实问答和介绍类需求。

典型 query：

- `许嵩什么时候生日`
- `王嘉尔出过几张专辑啊`
- `这首歌是谁唱的`
- `这首歌是什么时候发行的`
- `介绍一下张碧晨`

当前策略：

- 这类 query 不返回歌曲列表。
- 线上模型会直接返回自然语言回答。
- 对「这首歌」「他」「她」这类上下文问法，目前只能做意图判断；如果没有真实播放上下文，答案准确性会受限。

### 功能指令

支持基础播控和收藏意图识别。

典型 query：

- `暂停一下`
- `继续播放`
- `下一首`
- `声音大点`
- `单曲循环`
- `收藏下这首`
- `红心一下`

当前策略：

- 播控类返回固定确认话术，例如「好的，现在为你暂停播放」。
- 收藏类返回固定确认话术，例如「好的，已为你收藏这首歌」。
- 当前 demo 只做意图识别和回复，不真正控制播放器状态或写入用户收藏。

### 轻量多轮上下文

支持基于上一轮结果做简单追问和指代解析。

典型 query：

- `播放第二首`
- `收藏这首`
- `这首歌是谁唱的`
- `换一批更欢快的`
- `不要周杰伦，换一些别的`

当前策略：

- 前端保存最近几轮对话、上一轮歌曲列表和最近选中的歌曲。
- 每次请求把这些上下文传给后端。
- 后端会把上下文写入模型提示，辅助解析「他/她/这首/第几首/上一批」。
- 对「播放第几首」「收藏这首」这类明确引用，可以直接根据上一轮列表命中目标歌曲。
- 当前上下文保存在浏览器端，不依赖数据库，适合 Vercel serverless 部署。

### 闲聊兜底

支持普通聊天、夸奖、状态表达等非音乐动作。

典型 query：

- `你是真牛啊`
- `今天又下雨`
- `困了，想睡觉了`
- `推的歌还可以`

当前策略：

- 没有明确听歌、推荐、播放、搜索、收藏或音乐问答动作时，判为闲聊。
- 闲聊不强行推荐歌曲。
- 线上模型会直接返回自然语言回复。

## 3. 当前推荐策略特点

- 先判断用户想完成的动作，再判断 query 里的音乐词是不是实体。
- 对明确单曲播放，严格返回目标单曲，避免变成推荐列表。
- 对歌手搜索，允许同一歌手多首歌同时出现，避免只展示一首。
- 对相似推荐，使用「同作者、同圈层、同地域、同声音特征、同情绪意象」的分层策略。
- 对主题、情绪、语言、年代、场景类表达，优先识别为曲库限定推荐。
- 对播控、收藏、百科、闲聊等非出歌意图，返回 `groups=[]`，避免误出歌。
- 对多轮指代，优先使用浏览器保存的上一轮结果做解析。

## 4. 已知问题

### 响应速度

当前页面会等模型完整生成推荐结果后再展示歌曲列表。DeepSeek 通常需要几秒，Gemini 更慢，并且可能受地区限制。

歌曲列表出来后，播放器解析需要额外请求 Spotify / 网易云。当前已改为按需加载，用户点击「加载播放器」时才解析对应歌曲，避免一次性请求 12 首歌。

部署在 Vercel 后，还会受到 serverless 冷启动影响。隔一段时间没人访问后，第一次请求会更慢。

### 播放器稳定性

当前播放器主要依赖 Spotify Embed 和网易云外链播放器。

Spotify 的限制：

- Embed 不保证所有歌曲都能完整播放。
- 部分歌曲需要用户登录 Spotify。
- 部分歌曲受地区、版权或账号权限限制。
- 华语歌、翻唱、现场版、别名歌曲可能匹配不到准确 track。

网易云的限制：

- 外链播放器不支持很多 VIP 歌和版权受限歌曲。
- 外链 iframe 通常不能继承用户自己的会员登录权益。
- 有些歌即使搜索到 ID，也可能无法在外链播放器中播放。

因此，当前播放器适合作为外部播放入口和 demo 展示，不保证所有推荐歌曲都能稳定内嵌播放。

### Gemini 可用性

Gemini API 可能返回地区限制错误：

```text
User location is not supported for the API use.
```

这和代码无关，取决于 API、账号和网络出口区域。当前演示建议默认使用 DeepSeek。

### 上下文能力

当前 demo 支持轻量多轮上下文，但还不是完整多轮对话系统。

对于：

- `他那首歌`
- `她还有类似的吗`
- `现在这首歌是谁唱的`
- `给我跟他相似的艺人`

如果没有真实播放上下文或上一轮推荐状态，系统只能做有限判断。刷新页面、换设备或换浏览器后，上下文会丢失；复杂多轮推理仍可能不稳定。

### 推荐结果质量

当前推荐主要由 LLM 生成，没有接入正式曲库召回、版权库、用户画像、播放历史和排序模型。

因此：

- 结果适合验证意图理解和策略表达。
- 不等同于生产级推荐效果。
- 歌曲是否可播、是否有版权、是否符合目标曲库，需要后续接真实曲库系统验证。

## 5. 后续优化建议

### 短期优化

- 改为先返回意图和骨架，再异步补齐推荐结果。
- 歌曲列表先展示，播放器按需加载。（已完成基础版）
- 默认只用 DeepSeek，Gemini 作为可选模型。
- 播放器失败时展示明确原因和外部打开入口。
- 对线上链路增加耗时埋点，区分模型耗时、播放器解析耗时、Vercel 冷启动耗时。

### 中期优化

- 接入真实曲库搜索 API。
- 对歌曲、歌手、专辑做实体标准化。
- 建立自动评测和错误分析流程。
- 增强上下文状态，例如当前播放歌曲、上一轮推荐结果、用户刚刚点击/跳过的歌曲。
- 将相似推荐的分层策略沉淀成稳定策略模板。

### 长期优化

- 接入正式播放器 SDK，例如 Spotify Web Playback SDK。
- 支持用户登录、播放控制和收藏写入。
- 接入用户画像、播放历史、收藏、跳过等反馈信号。
- 建立「召回 + 排序 + LLM 解释」的混合推荐链路。
- 将 demo 升级为可持续评测和可灰度上线的音乐助手服务。
